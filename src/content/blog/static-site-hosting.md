## そもそも Web サーバーとは

ブラウザとサーバーは別々のプログラムで、`http` という約束事で会話している。

1. ブラウザが「この URL の中身をください」とリクエストを送る
2. その住所で待ち受けているサーバーが受け取る
3. サーバーが対応する HTML を用意する
4. レスポンスとして返す
5. ブラウザが受け取った HTML を描画する

データ分析でいう `response = request(url, params)` の往復。
Web サーバーはその「返す側」を担当するプログラム、と考えると分かりやすい。
ポイントは 3 の「用意する」で、ここに2つのやり方がある。

## 動的サイトと静的サイト

| | サーバーが返すもの | 必要なもの | 例 |
|---|---|---|---|
| 動的 | リクエストのたびに、その場で組み立てた HTML | 常時稼働するサーバー + たいてい DB | ログイン後のマイページ、検索結果 |
| 静的 | 事前に用意した HTML ファイルをそのまま | ファイルを保管して返せる場所だけ | このブログ |

動的は「注文が入ってから調理する」レストラン。
静的は「作り置きを棚に並べておく」売店。
中身が閲覧者によって変わらないなら、注文ごとに調理するのは全部無駄になる。

## だから配信先が軽くて済む

静的サイトは、ビルドの時点で全ページの HTML を作り終えている
(Astro なら `dist/` フォルダがそれ)。配信時の仕事は
「URL に対応するファイルを読んで返す」だけ。

つまり、置き場所は「ファイルを保管して返せる」だけの場所で足りる。

- オブジェクトストレージ(S3 / Cloudflare R2 など。データ分析での GCS と同じ役割)
- 静的ホスティングサービス(Cloudflare Workers / GitHub Pages など。無料枠あり)
- CDN(世界中に置いたキャッシュサーバー群)

## 速い・安い・壊れにくい、の中身

- **速い**: リクエストのたびに計算しない。さらに CDN が使えるので、
  閲覧者から地理的に近いサーバーがファイルを返せる。
- **安い**: 常時起動のサーバー代も、DB の維持費もかからない。
  アクセスがない間のコストがほぼゼロ。
- **壊れにくい**: 動いているプログラムがない。
  プロセスが落ちる・依存サービスが応答しない・アプリの脆弱性を突かれる、
  といった「動いているもの」に起因する障害の対象がそもそも存在しない。

もちろん万能ではない。閲覧者ごとに中身を変える、フォーム投稿を受け取って
保存する、といったことは静的だけではできない
(このサイトの検索が「ブラウザ側の JS だけ」で完結しているのはそのため)。

## dev / build / preview の役割分担

Astro の3つのコマンドは、この話にそのまま対応している。

| コマンド | 何をするか | 位置づけ |
|---|---|---|
| `npm run dev` | 開発用サーバー。保存で自動更新など補助が多い | 開発中だけ使う特別版 |
| `npm run build` | 元ファイル → `dist/` に完成品の HTML 一式を吐く | 「作り置き」を作る工程 |
| `npm run preview` | `dist/` をただ返すだけの簡易サーバー | 本番に一番近い動作確認 |

そして「デプロイ」とは、`build` で作った `dist/` を
上のような「ファイル置き場」に置く最後の一歩のこと。
このサイトはそれを GitHub の仕組みで自動化した
(別記事「GitHub Pages に自動デプロイする」)。
